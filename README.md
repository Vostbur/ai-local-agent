# AI Local Agent

Локальный AI-агент для повседневных задач. Работает полностью на вашем компьютере: ни документы, ни заметки, ни фотографии не покидают вашу машину.

## Что умеет сейчас

- **Сохранять заметки** в Markdown-файлы (`save_note`). Существующие заметки никогда не перезаписываются: при совпадении имени добавляется числовой суффикс.
- **Искать заметки по названию** (`read_notes`) — по заголовку и имени файла, с учётом русских словоформ.
- **Искать по содержимому** (`search_notes`) — с фрагментом контекста и числом совпадений.
- Работать с **локальной моделью** через [Ollama](https://ollama.com).
- **Не вызывать инструменты зря**: на посторонние вопросы вроде «какая погода» агент отвечает без `tool_call`.
- **Не зацикливаться** на повторных вызовах: одинаковый вызов инструмента с теми же аргументами пропускается (шаг 6.1).
- Вести **логи** своих действий в `logs/agent.log`.

## Что появится позже

- Анализ PDF-документов и создание новых документов по их подобию.
- Сортировка фотографий по содержимому.
- Полноценный RAG (поиск по смыслу через эмбеддинги) по документам.

Текущий статус и план — в файле `TASKS.md`.

## Установка с нуля (для новичка)

Все команды ниже выполняются в терминале. На Windows удобно использовать **PowerShell**, на macOS/Linux — **Terminal**.

### Шаг 1. Скачайте проект

Если вы уже скопировали папку проекта — переходите к шагу 2. Иначе:

```bash
git clone <адрес-вашего-репозитория> ai-local-agent
cd ai-local-agent
```

Если git не установлен, просто скачайте архив с проектом и распакуйте его, затем откройте терминал в распакованной папке.

### Шаг 2. Установите Ollama и загрузите модель

Установите Ollama с официального сайта.

Убедитесь, что Ollama работает. В терминале:

```bash
ollama --version
```

Должна отобразиться версия. Если команда не найдена — перезапустите терминал.

Загрузите модель:

```bash
ollama pull qwen2.5:3b
```

Займёт несколько минут и около 2 ГБ.

Проверьте, что модель работает:

```bash
ollama run qwen2.5:3b "Привет"
```

Модель должна ответить. Выйти из интерактивного режима — Ctrl+D (macOS/Linux) или `/bye` (Windows).

### Шаг 3. Создайте модель с увеличенным контекстом

Агенту нужен контекст больше стандартного. В корне проекта создайте файл `Modelfile` со следующим содержимым:

```dockerfile
FROM qwen2.5:3b
PARAMETER num_ctx 8192
```

Соберите модель под новым именем:

```bash
ollama create qwen2.5-3b-agent -f Modelfile
```

Проверьте:

```bash
ollama list
```

В списке должна появиться `qwen2.5-3b-agent`.

### Шаг 4. Создайте виртуальное окружение Python

Виртуальное окружение — это изолированная папка с библиотеками, чтобы не засорять систему.

```bash
python -m venv .venv
```

Активируйте его:

**Windows (PowerShell):**

```powershell
.venv\Scripts\Activate.ps1
```

Если PowerShell ругается на политику выполнения, один раз выполните:

```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

**Windows (cmd):**

```cmd
.venv\Scripts\activate.bat
```

**macOS / Linux:**

```bash
source .venv/bin/activate
```

В начале строки терминала появится `(.venv)`. Это значит, что вы внутри окружения.

### Шаг 5. Установите зависимости

```bash
pip install -r requirements.txt
```

### Шаг 6. Создайте локальный файл настроек

```bash

cp config/settings.example.toml config/settings.toml

# Windows (PowerShell)
Copy-Item config\settings.example.toml config\settings.toml
```

Файл `config/settings.toml` не попадает в git — это ваши личные настройки.

### Шаг 7. Проверьте, что всё работает

Запустите тесты:

```bash
pytest -v
```

Все тесты должны быть зелёными. Если что-то падает — смотрите раздел «Проблемы и решения» ниже.

Запустите агент с одной задачей (реальная модель):

Первый запуск может занять несколько минут: модель загружается в память, а генерация на CPU медленная. В итоге в `data/notes/` появится файл с заметкой, а в консоли — строка вида `Готово: ...`.

Если что-то не работает — смотрите раздел «Проблемы и решения» ниже.

## Как пользоваться агентом

### Запуск одной задачи

```bash
python scripts/run_agent.py "Сохрани заметку 'Список покупок' с текстом 'Молоко, хлеб, яйца'"
```

Скрипт выполнит цель, напечатает финальный ответ и (если инструмент вернул путь) — путь к созданному файлу.

### Интерактивный режим

```bash
python scripts/run_agent.py
```

Скрипт запустится один раз и будет спрашивать цели одну за другой. Модель остаётся загруженной в память, поэтому следующие задачи выполняются быстрее, чем при повторном запуске скрипта.

```
AI Local Agent (модель: qwen2.5-3b-agent)
Введите цель или /quit для выхода.
> сохрани заметку про встречу в понедельник
[...] выполняется, подождите (на CPU это может занять несколько минут)
Готово: Заметка сохранена.
Шагов: 2
> /quit
Выход.
```

Для выхода: `/quit`, `/exit`, `exit`, `quit`, `Ctrl+C` или `Ctrl+D`.

### Типичные проблемы при запуске

- **Ollama не отвечает.** Запустите `ollama serve` в отдельном терминале — Ollama не запущен. Запустите его и повторите.
- **Не найден `config/settings.toml`** — скопируйте `config/settings.example.toml` в `config/settings.toml`.
- **Достигнут лимит шагов** — модель не смогла дойти до финала за `max_steps` шагов. Сформулируйте цель точнее или увеличьте `max_steps` в `config/settings.toml`.

## Что происходит после запуска команды — пошаговый разбор

Этот раздел — учебный. Он показывает весь путь от нажатия Enter до появления файла с заметкой: какие функции вызываются, в каком порядке, какие данные передаются между ними. Если вы новичок в программировании, читайте его после того, как хотя бы один раз успешно запустили агента — так будет понятнее.

### Команда, которую мы разбираем

```bash
python scripts/run_agent.py "Сохрани заметку 'Тест запуска' с текстом 'Привет'"
```

Что здесь есть:

- `python` — интерпретатор Python. Он читает файл и выполняет его построчно.
- `scripts/run_agent.py` — файл, который мы запускаем. Это точка входа, «кнопка включения» агента.
- `"Сохрани заметку 'Тест запуска' с текстом 'Привет'"` — **аргумент командной строки**, то есть цель, которую получит агент. Кавычки нужны, чтобы оболочка не разбила фразу на отдельные слова.

### Общая картина

Условно весь путь делится на три фазы:

1. **Подготовка.** Python читает конфиг, настраивает логи, собирает оркестратор с инструментами и моделью.
2. **Работа агента.** Оркестратор в цикле общается с Ollama. Модель решает вызвать `save_note`, оркестратор вызывает функцию, возвращает результат модели, модель говорит «готово».
3. **Завершение.** Оркестратор возвращает результат, скрипт печатает его и выходит.

Ниже — подробно по шагам.

---

### Шаг 1. Python запускает `run_agent.py`

Когда вы вводите команду, Python:

1. Открывает `scripts/run_agent.py`.
2. Дочитывает до конца файла и находит блок:
   ```python
   if __name__ == "__main__":
       main()
   ```
3. Вызывает функцию `main()`. Это первая **наша** функция, которая начинает работу.

Параллельно Python автоматически импортирует всё, что указано в верхней части файла:

- `sys`, `argparse`, `logging` — стандартные библиотеки Python;
- `load_config` из `src/agent/config.py`;
- `setup_logging` из `src/agent/logging_setup.py`;
- `build_orchestrator` из `src/agent/app.py`;
- `MaxStepsExceeded` из `src/agent/orchestrator.py`.

Импорт — это «подключение» файла: Python читает его и делает доступными функции и классы. Ничего не выполняется, кроме определений функций и классов.

### Шаг 2. `main()` разбирает аргументы командной строки

```python
parser = argparse.ArgumentParser(description="AI Local Agent")
parser.add_argument("goal", nargs="?", help="...")
args = parser.parse_args()
```

- `argparse` — стандартный модуль для разбора аргументов командной строки. Он умеет понимать `--help`, `--flag`, позиционные аргументы.
- `add_argument("goal", nargs="?")` говорит: «у нас есть позиционный аргумент `goal`, но он необязательный (`?`)».
- `parse_args()` берёт список слов после `python scripts/run_agent.py` и раскладывает их по полям. В нашем случае `args.goal == "Сохрани заметку 'Тест запуска' с текстом 'Привет'"`.

Если бы аргумента не было, `args.goal` был бы `None`, и `main()` перешёл бы в интерактивный режим. Но у нас аргумент есть — идём дальше.

### Шаг 3. `load_config()` читает настройки

```python
try:
    config = load_config()
except FileNotFoundError:
    print("Не найден config/settings.toml. ...")
    sys.exit(1)
```

`load_config()` живёт в `src/agent/config.py` и делает следующее:

1. Определяет путь к файлу: `config/settings.toml` относительно корня проекта.
2. Открывает файл и читает TOML через стандартный `tomllib` (встроен в Python 3.11+, ничего ставить не нужно).
3. Превращает прочитанные данные в датаклассы:
   - `LLMConfig(provider, model, base_url, max_steps)` — настройки модели;
   - `PathsConfig(data_dir, notes_dir, inbox_dir, photos_dir, logs_dir)` — куда класть файлы;
   - `SafetyConfig(confirm_file_operations)` — флаги безопасности;
   - `AppConfig(llm, paths, safety)` — обёртка над всеми тремя.
4. Возвращает `AppConfig`.

Если файла нет — `FileNotFoundError`, `main()` печатает подсказку и выходит с кодом 1 (это код ошибки; 0 — успех).

Ключевой момент: `config` — это не словарь и не «сырой» текст. Это объект, в котором по атрибутам доступны конкретные значения: `config.llm.model`, `config.paths.notes_dir`, `config.llm.max_steps`. Такой подход называется **типизированной конфигурацией**: IDE подсказывает поля, а опечатки ловятся сразу, а не «где-то в рантайме».

### Шаг 4. `setup_logging()` готовит логи

```python
logger = setup_logging(config.paths.logs_dir)
```

Функция из `src/agent/logging_setup.py`:

1. Создаёт папку `logs/`, если её нет.
2. Настраивает глобальный логгер с именем `"agent"` (он один на весь проект).
3. Добавляет два обработчика: файл `logs/agent.log` (UTF-8, режим `append` — дописывать в конец) и консоль.
4. Устанавливает формат строки: `время | уровень | имя логгера | сообщение`.
5. Возвращает логгер.

С этого момента любая строка `logger.info("...")` попадёт и в файл, и в консоль. Внутри `setup_logging` есть защита от дубликатов: если функция вызвана повторно, она не добавит вторые обработчики. Иначе каждая запись появлялась бы в логе дважды.

### Шаг 5. `build_orchestrator()` собирает агента

```python
orchestrator = build_orchestrator(config, logger)
```

Функция из `src/agent/app.py` — центральное место сборки. Она делает пять вещей.

**5.1. Создаёт реестр инструментов.**

```python
registry = ToolRegistry()
```

`ToolRegistry` (из `src/agent/registry.py`) — это словарь вида `{имя: ToolDefinition}` плюс методы для работы с ним. Пока он пустой.

**5.2. Регистрирует все три инструмента.**

```python
registry.register(SAVE_NOTE_TOOL)
registry.register(READ_NOTES_TOOL)
registry.register(SEARCH_NOTES_TOOL)
```

Каждая константа — это `ToolDefinition` из соответствующего модуля в `src/agent/tools/`:

- `SAVE_NOTE_TOOL` (`save_note.py`): `name="save_note"`, описание и схема с `title`, `content`.
- `READ_NOTES_TOOL` (`read_notes.py`): `name="read_notes"`, описание и схема с опциональным `query`.
- `SEARCH_NOTES_TOOL` (`search_notes.py`): `name="search_notes"`, описание и схема с `query` (required) и `max_results` (optional).

Каждое описание содержит русские и английские триггеры и явное противопоставление: `read_notes` — по названию, `search_notes` — по содержимому. Это нужно, чтобы 3B-модель не путала инструменты.

**5.3. Готовит список инструментов для модели.**

```python
tools = [SAVE_NOTE_TOOL, READ_NOTES_TOOL, SEARCH_NOTES_TOOL]
```

Этот список передаётся в `OllamaLLM`, чтобы тот отправил описания инструментов модели. Модель «видит» инструмент только через этот список. Важно: `registry` и `tools` должны содержать **одни и те же** `ToolDefinition`. Если добавить инструмент в `registry`, но забыть в `tools`, модель о нём не узнает. Поэтому в `build_orchestrator` оба списка собираются из одного источника.

**5.4. Создаёт клиент к Ollama.**

```python
llm = OllamaLLM(model=config.llm.model, base_url=config.llm.base_url, tools=tools)
```

`OllamaLLM` (из `src/agent/llm_ollama.py`) — обёртка над HTTP-запросами к Ollama. В конструкторе ничего не отправляется: он только запоминает `model`, `base_url`, `tools` и таймаут. Реальный запрос произойдёт, когда оркестратор вызовет `llm.chat(...)`.

**5.5. Создаёт оркестратор.**

```python
return Orchestrator(
    llm=llm,
    registry=registry,
    logger=logger,
    max_steps=config.llm.max_steps,
    tool_context={
        "save_note": {"notes_dir": config.paths.notes_dir},
        "read_notes": {"notes_dir": config.paths.notes_dir},
        "search_notes": {"notes_dir": config.paths.notes_dir},
    },
)
```

`Orchestrator` (из `src/agent/orchestrator.py`) — «дирижёр». Он получает клиент к модели, реестр инструментов, логгер, лимит шагов и **контекст инструментов**.

`tool_context` — важная деталь. Это словарь `{имя_инструмента: {доп_аргументы}}`. Он нужен, чтобы модель не передавала `notes_dir` сама. Путь к заметкам — это настройка, а не часть запроса пользователя. Модель будет вызывать `save_note(title=..., content=...)`, а оркестратор добавит `notes_dir=config.paths.notes_dir` **из конфига**. Так модель не сможет случайно записать файл в неожиданное место.

`build_orchestrator` возвращает готовый `Orchestrator`, и `main()` сохраняет его в переменную `orchestrator`.

### Шаг 6. `main()` вызывает `_run_one()`

```python
if args.goal:
    _run_one(orchestrator, args.goal, logger)
    return
```

Поскольку `args.goal` не пуст, `main()` вызывает `_run_one` и выходит. `_run_one` — вспомогательная функция в том же файле. Она нужна, чтобы одна и та же логика «выполнить одну задачу и напечатать результат» использовалась и в режиме одной задачи, и в интерактивном цикле.

`_run_one` сначала печатает предупреждение:

```
[...] выполняется, подождите (на CPU это может занять несколько минут)
```

Это не косметика. На CPU первая задача действительно может занять 1–3 минуты: Ollama загружает модель в память. Если ничего не напечатать, пользователь решит, что скрипт завис.

Затем `_run_one` вызывает главный метод:

```python
result = orchestrator.run(goal)
```

### Шаг 7. `Orchestrator.run()` — начало цикла

Это сердце агента. Метод `run` из `src/agent/orchestrator.py` делает следующее.

**7.1. Инициализирует историю сообщений с системным промптом.**

```python
messages = [
    {"role": "system", "content": SYSTEM_PROMPT},
    {"role": "user", "content": goal},
]
```

`SYSTEM_PROMPT` — константа в `orchestrator.py`. Она содержит четыре правила:

1. Вызывать инструмент только если это необходимо.
2. После успешного вызова проверить, достигнута ли цель; если да — дать финальный ответ обычным текстом.
3. Никогда не вызывать один и тот же инструмент с одинаковыми аргументами дважды.
4. Правило выбора: `read_notes` для названий и заголовков, `search_notes` для содержимого.

Это первое сообщение в каждом диалоге — модель видит его при каждом `chat`. Системный промпт — основной инструмент для стабилизации 3B-модели; без него она гораздо чаще зацикливается и путает инструменты.

**7.2. Запускает цикл до `max_steps`.**

```python
executed_calls: set[str] = set()
for step in range(1, self.max_steps + 1):
```

`max_steps` берётся из конфига (по умолчанию 10). Лимит защищает от бесконечного цикла.

`executed_calls` — множество ключей уже выполненных вызовов в рамках этой задачи. Живёт только внутри `run`, не переносится между задачами. Нужно для защиты от повторных вызовов (шаг 7.6).

**7.3. Отправляет историю модели.**

```python
response = self.llm.chat(messages)
```

`self.llm` — это наш `OllamaLLM`. Его метод `chat`:

1. Преобразует `tools` в формат OpenAI (`{"type": "function", "function": {...}}`).
2. Формирует тело POST-запроса:
   ```json
   {
     "model": "qwen2.5-3b-agent",
     "messages": [...],
     "tools": [...],
     "tool_choice": "auto",
     "stream": false
   }
   ```
3. Отправляет `POST http://localhost:11434/v1/chat/completions` через библиотеку `requests`.
4. Ждёт ответ. На CPU это может занять десятки секунд.
5. Разбирает JSON-ответ и возвращает `LLMResponse`.

**7.4. Модель решает вызвать инструмент.**

Ollama передаёт запрос модели `qwen2.5-3b-agent`. Модель читает системный промпт, цель, видит три инструмента с описаниями и схемами и решает: «нужно вызвать `save_note` с аргументами `title="Тест запуска"`, `content="Привет"`».

Ollama возвращает JSON примерно такого вида:

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "tool_calls": [{
        "id": "call_1",
        "type": "function",
        "function": {
          "name": "save_note",
          "arguments": "{\"title\": \"Тест запуска\", \"content\": \"Привет\"}"
        }
      }]
    }
  }]
}
```

Обратите внимание: `arguments` — это **строка** с JSON внутри, а не готовый словарь. Так устроен OpenAI-совместимый формат. `OllamaLLM.chat` делает `json.loads(...)` и возвращает:

```python
LLMResponse(
    type="tool_call",
    tool_name="save_note",
    tool_arguments={"title": "Тест запуска", "content": "Привет"},
)
```

Оркестратор получает этот объект.

**7.5. Оркестратор готовит аргументы.**

Сначала смотрит на `response.type`. Это `"tool_call"`, значит, модель просит вызвать инструмент. Оркестратор:

1. Достаёт контекст:
   ```python
   extra = self.tool_context.get("save_note", {})
   # extra == {"notes_dir": Path("data/notes")}
   ```
2. Сливает аргументы модели с контекстом:
   ```python
   arguments = {**response.tool_arguments, **extra}
   # arguments == {"title": "Тест запуска", "content": "Привет", "notes_dir": Path("data/notes")}
   ```
   Порядок важен: `extra` идёт **после**, поэтому контекст перекрывает аргументы модели. Если бы модель попыталась передать `notes_dir="C:/Windows"`, контекст бы это перекрыл. Это защита от prompt injection и просто от ошибок модели.

**7.6. Проверка на повторный вызов.**

Перед вызовом инструмента оркестратор строит «ключ вызова»:

```python
call_key = f"{response.tool_name}:{sorted((k, str(v)) for k, v in arguments.items())}"
```

`str(v)` нужен, потому что `notes_dir` — это `Path`, а `sorted` убирает зависимость от порядка ключей в словаре. Ключ — строка вида `"save_note:[('content', 'Привет'), ('notes_dir', 'data\\notes'), ('title', 'Тест запуска')]"`.

Дальше:

- Если `call_key in executed_calls` — инструмент **не вызывается**. Модели возвращается:
  ```
  tool_result: ALREADY_EXECUTED: инструмент 'save_note' уже был вызван с этими аргументами. Не вызывай его снова — дай финальный ответ.
  ```
- Иначе — инструмент вызывается, а `call_key` добавляется в `executed_calls`.

Это детерминированная защита (шаг 6.1). Системный промпт из шага 7.1 её дублирует на уровне модели, но детектор страхует, если 3B-модель проигнорирует инструкцию. В комбинации они дают почти полное отсутствие зацикливаний.

**7.7. Оркестратор вызывает инструмент.**

```python
try:
    result = self.registry.call(response.tool_name, **arguments)
    tool_succeeded = True
except Exception as exc:
    result = f"ERROR: {exc}"
    tool_succeeded = False
    logger.exception(...)
```

Если инструмент бросил исключение, оркестратор **не падает**: ошибка ловится и превращается в строку `ERROR: ...`, которая попадёт модели. Это принципиально: агент должен продолжать работу, даже если один вызов неудачен.

### Шаг 8. `ToolRegistry.call()` вызывает функцию

`registry.call` (из `src/agent/registry.py`) делает три вещи:

1. `tool = self.get("save_note")` — находит `ToolDefinition` по имени. Если имени нет — `KeyError`.
2. `func = tool.func` — достаёт саму Python-функцию.
3. `return func(**arguments)` — вызывает её с распакованными именованными аргументами. `**arguments` означает «разложи словарь на именованные аргументы»: `save_note(title="Тест запуска", content="Привет", notes_dir=Path("data/notes"))`.

Формально `registry.call` — тонкая обёртка. Но она нужна: во-первых, оркестратор не знает имён функций заранее (модель возвращает имя строкой), во-вторых, в одном месте собрана проверка «инструмент зарегистрирован». Если бы оркестратор вызывал `save_note(...)` напрямую, он был бы жёстко привязан к одному инструменту и не смог бы работать с `read_notes`, `search_notes` и другими.

### Шаг 9. `save_note()` создаёт файл

Теперь работает функция из `src/agent/tools/save_note.py`. Пошагово:

1. **Проверка заголовка.**
   ```python
   if not title.strip():
       raise ValueError("title must not be empty")
   ```
   Если `title` пустой или состоит из пробелов — ошибка. Оркестратор её поймает и вернёт модели как `ERROR: title must not be empty`.

2. **Создание папки.**
   ```python
   notes_dir.mkdir(parents=True, exist_ok=True)
   ```
   `parents=True` — создать все промежуточные папки (`data/`, потом `data/notes/`). `exist_ok=True` — не падать, если папка уже есть.

3. **Генерация slug — безопасного имени файла.**
   - Приведение к нижнему регистру: `"Тест запуска"` → `"тест запуска"`.
   - Замена пробелов на `_`: `"тест_запуска"`.
   - Удаление запрещённых символов `< > : " / \ | ? *` и управляющих.
   - Сохранение Unicode: кириллица остаётся кириллицей (в Python 3 `\w` в регулярках по умолчанию включает Unicode-буквы).
   - Обрезка до 100 символов.
   - Если после чистки пусто — `"note"`.

   Для нашего примера slug — `"тест_запуска"`.

4. **Поиск свободного имени.**
   ```python
   path = notes_dir / f"{slug}.md"
   i = 1
   while path.exists():
       path = notes_dir / f"{slug}_{i}.md"
       i += 1
   ```
   Если `тест_запуска.md` уже есть, берётся `тест_запуска_1.md`, потом `_2` и так далее. **Файл никогда не перезаписывается** — это главное требование к инструменту.

5. **Запись содержимого.**
   ```python
   path.write_text(f"# {title}\n\n{content}\n", encoding="utf-8")
   ```
   `encoding="utf-8"` критичен на Windows: без него кириллица запишется в кодировке системы и потом будет читаться как «кракозябры».

6. **Возврат пути.**
   ```python
   return path
   ```
   Функция возвращает `Path("data/notes/тест_запуска.md")` (или с суффиксом). Это значение попадёт обратно в `registry.call`, затем в оркестратор.

### Шаг 10. Оркестратор возвращает результат модели

Вернувшись в `Orchestrator.run`, оркестратор:

1. Записывает результат в лог: `logger.info(f"tool save_note -> {result}")`.
2. Определяет статус:
   ```python
   status = "SUCCESS" if tool_succeeded else "ERROR"
   ```
3. Добавляет в `messages` **два** сообщения:
   ```python
   messages.append({
       "role": "assistant",
       "content": f"tool_call: {response.tool_name}({arguments})",
   })
   messages.append({
       "role": "user",
       "content": (
           f"tool_result: {status}. {response.tool_name} returned: {result}. "
           f"If this satisfies the user's goal, respond with a final answer now."
       ),
   })
   ```
   Это имитация диалога: «ассистент попросил вызвать инструмент» → «пользователь сообщает результат». Модель увидит эту пару в следующем запросе и поймёт, что инструмент отработал.

   Почему так: для 3B-модели голая строка `tool_result: <путь>` часто не выглядит как «успех», и она вызывает инструмент повторно. Явное `SUCCESS` и фраза `respond with a final answer now` — маленькая, но заметная подсказка. При ошибке статус становится `ERROR`, и модель видит, что инструмент не сработал.

4. Сохраняет `str(result)` в `tool_results` — чтобы потом `run_agent.py` мог напечатать путь к файлу.

5. **Переходит на следующую итерацию цикла.** Снова вызывает `llm.chat(messages)`, но теперь `messages` содержит четыре сообщения: system, цель, `tool_call`, `tool_result`.

### Шаг 11. Второй запрос к модели — финал

`OllamaLLM.chat` снова отправляет POST в Ollama с расширенной историей. Модель видит:

- системный промпт (правила);
- пользователь попросил сохранить заметку;
- она (модель) попросила вызвать `save_note`;
- инструмент вернул путь к файлу со статусом `SUCCESS`.

Модель решает: «задача выполнена, инструмент больше не нужен». Ollama возвращает JSON без `tool_calls`, только с текстом:

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": "Заметка сохранена."
    }
  }]
}
```

`OllamaLLM.chat` видит, что `tool_calls` нет, и возвращает:

```python
LLMResponse(type="final", content="Заметка сохранена.")
```

Оркестратор получает `response.type == "final"` и:

1. Логирует финал.
2. Возвращает:
   ```python
   OrchestratorResult(
       success=True,
       final_answer="Заметка сохранена.",
       steps_used=2,
       tool_results=["data/notes/тест_запуска.md"],
   )
   ```
   `steps_used=2` — потому что было два обращения к модели: первое с `tool_call`, второе с `final`. Это нормально: один шаг — одно обращение.

Цикл завершён, `Orchestrator.run` возвращает управление в `_run_one`.

### Шаг 12. `_run_one` печатает результат

```python
if result.success:
    print(f"Готово: {result.final_answer}")
    print(f"Шагов: {result.steps_used}")
    if result.tool_results:
        print(f"Результаты инструментов: {result.tool_results}")
```

В консоли появляется:

```
[...] выполняется, подождите (на CPU это может занять несколько минут)
Готово: Заметка сохранена.
Шагов: 2
Результаты инструментов: ['data/notes/тест_запуска.md']
```

`_run_one` возвращает управление в `main()`. Поскольку `args.goal` был задан, `main()` делает `return` и завершается. Python доходит до конца файла и выходит с кодом 0.

### Шаг 13. Что осталось на диске

После выполнения команды:

- **`data/notes/тест_запуска.md`** — новая заметка. Содержимое:
  ```markdown
  # Тест запуска

  Привет
  ```
  Если запустить команду повторно с тем же заголовком, появится `тест_запуска_1.md` — первый файл не изменится.

- **`logs/agent.log`** — строки вида:
  ```
  2026-10-25 12:34:56,789 | INFO | agent | step=1 type=tool_call
  2026-10-25 12:34:58,012 | INFO | agent | tool save_note -> data/notes/тест_запуска.md
  2026-10-25 12:35:10,345 | INFO | agent | step=2 type=final
  2026-10-25 12:35:10,346 | INFO | agent | final: Заметка сохранена.
  ```

- **`config/settings.toml`, `data/`, `logs/`** — не попадают в git (они в `.gitignore`). Ваши личные данные остаются локально.

### Полная цепочка вызовов (краткая схема)

```
python scripts/run_agent.py "<цель>"
└── run_agent.main()
    ├── argparse.parse_args() → args.goal
    ├── config.load_config() → AppConfig
    ├── logging_setup.setup_logging() → logger
    ├── app.build_orchestrator(config, logger)
    │   ├── ToolRegistry()
    │   ├── registry.register(SAVE_NOTE_TOOL | READ_NOTES_TOOL | SEARCH_NOTES_TOOL)
    │   ├── OllamaLLM(model, base_url, tools=[все три])
    │   └── Orchestrator(llm, registry, logger, max_steps, tool_context)
    ├── run_agent._run_one(orchestrator, goal, logger)
    │   └── orchestrator.run(goal)
    │       ├── messages = [system, user(goal)]
    │       ├── for step in 1..max_steps:
    │       │   ├── llm.chat(messages) → tool_call | final
    │       │   ├── if final: return OrchestratorResult(success=True, ...)
    │       │   ├── if tool_call:
    │       │   │   ├── call_key = tool + sorted(args)
    │       │   │   ├── if call_key in executed_calls: result = "ALREADY_EXECUTED..."
    │       │   │   └── else: result = registry.call(tool, **args)
    │       │   └── messages += [assistant(tool_call), user(tool_result)]
    │       └── raise MaxStepsExceeded
    └── print("Готово: ...")
```

### Где что искать в коде

| Что происходит | Файл | Функция / класс |
| :--- | :--- | :--- |
| Точка входа | `scripts/run_agent.py` | `main`, `_run_one` |
| Разбор аргументов | `scripts/run_agent.py` | `argparse` в `main` |
| Чтение конфига | `src/agent/config.py` | `load_config`, `AppConfig` |
| Логирование | `src/agent/logging_setup.py` | `setup_logging` |
| Сборка агента | `src/agent/app.py` | `build_orchestrator` |
| Цикл «цель → инструмент → результат» | `src/agent/orchestrator.py` | `Orchestrator.run`, `SYSTEM_PROMPT` |
| Клиент к Ollama | `src/agent/llm_ollama.py` | `OllamaLLM.chat` |
| Формат ответа модели | `src/agent/llm.py` | `LLMResponse` |
| Реестр инструментов | `src/agent/registry.py` | `ToolRegistry.call`, `ToolDefinition` |
| Сохранение заметки | `src/agent/tools/save_note.py` | `save_note`, `SAVE_NOTE_TOOL` |
| Поиск по названию | `src/agent/tools/read_notes.py` | `read_notes`, `READ_NOTES_TOOL` |
| Поиск по содержимому | `src/agent/tools/search_notes.py` | `search_notes`, `SEARCH_NOTES_TOOL` |
| Стемминг и сравнение | `src/agent/tools/_search.py` | `find_match`, `find_match_with_kind` |

### Что важно понять из этого разбора

1. **Агент — это цикл, а не один запрос.** Модель вызывается минимум дважды: сначала чтобы выбрать инструмент, потом чтобы подтвердить финал. В сложных задачах — больше.
2. **Модель не пишет код и не трогает файлы напрямую.** Она только возвращает структурированный «запрос на вызов». Всё остальное делает Python-код. Это ключевое отличие агента от «чат-бота с плагинами».
3. **Контекст инструментов — это защита.** Модель не знает и не должна знать, куда сохранять файлы. Путь приходит из конфига. Даже если модель попытается подменить `notes_dir`, `{**args, **extra}` перекроет её аргумент.
4. **Системный промпт и детектор повторов — две линии защиты от зацикливания.** Системный промпт убеждает модель не повторяться, детектор (`executed_calls`) гарантирует это на уровне кода. На 3B нужны обе.
5. **Логи — ваш главный инструмент отладки.** Если агент «не работает», почти всегда ответ в `logs/agent.log`: какой тип ответа вернула модель, какой инструмент вызвала, с какими аргументами, что вернулось.
6. **Медленно — это нормально.** На CPU 3B-модель генерирует 5–15 токенов в секунду. Два обращения к модели в нашем примере могут занять 1–3 минуты, особенно первый раз, когда модель загружается в память.

## Работа с заметками: сохранение, поиск, чтение

Агент работает с заметками в папке `data/notes/` через три инструмента:

| Инструмент | Что делает | Когда используется |
| :--- | :--- | :--- |
| `save_note` | Сохраняет новую заметку в Markdown-файл. Никогда не перезаписывает существующие: при совпадении имени добавляет `_1`, `_2` и т.д. | «Сохрани заметку…», «Запиши…», «Создай заметку…» |
| `read_notes` | Ищет заметки по названию (заголовку и имени файла). Возвращает путь, заголовок и краткий фрагмент тела. | «Покажи заметки про…», «Есть ли заметка под названием…», «Покажи все заметки» |
| `search_notes` | Ищет по содержимому заметок. Возвращает путь, заголовок, фрагмент с контекстом и число совпадений. | «Найди, что я писал про…», «В какой заметке я упоминал…» |

Поиск учитывает русские словоформы: «покупки» найдёт «Список покупок», «документы» — «для документов». Это не полноценный стемминг, но для заметок работает в большинстве случаев.

### Примеры запуска

Все команды ниже выполняются в терминале из корня проекта. Виртуальное окружение активировано, Ollama запущен.

**Сохранение новой заметки**

```bash
python scripts/run_agent.py "Сохрани заметку 'Список покупок' с текстом 'Молоко, хлеб, яйца'"
```

Создаст `data/notes/список_покупок.md` с содержимым:

```markdown
# Список покупок

Молоко, хлеб, яйца
```

**Сохранение второй заметки с тем же названием**

```bash
python scripts/run_agent.py "Сохрани заметку 'Список покупок' с текстом 'Ещё один список'"
```

Создаст `список_покупок_1.md`. Первый файл не изменится — это гарантия инструмента.

**Поиск по названию**

```bash
python scripts/run_agent.py "Покажи заметки про покупки"
```

Агент вызовет `read_notes(query="покупки")` и найдёт `список_покупок.md`, несмотря на разницу в окончании.

**Поиск по содержимому**

```bash
python scripts/run_agent.py "В какой заметке я упоминал документы?"
```

Агент вызовет `search_notes(query="документы")` и вернёт заметку «Идеи проекта» с фрагментом «…Сделать локального агента для документов».

**Показать все заметки**

```bash
python scripts/run_agent.py "Покажи все заметки"
```

`read_notes` с пустым `query` вернёт до 50 заметок с путями, заголовками и фрагментами.

**Проверка, что агент не вызывает инструменты зря**

```bash
python scripts/run_agent.py "Какая сегодня погода?"
```

Агент ответит, что прогноз погоды вне его возможностей, и не вызовет ни один инструмент. Это важное свойство: модель не «притягивает» любую задачу к заметкам.

### Интерактивный режим — несколько задач подряд

```bash

```

### Как понять, что агент выбрал правильный инструмент

Каждый запуск пишет лог в `logs/agent.log`. Найдите строки:

```
step=1 type=tool_call
tool read_notes -> [...]
step=2 type=final
```

`type=tool_call` и `tool_name` — какой инструмент выбрала модель.

`tool <name> -> <result>` — что инструмент вернул.

`step=2 type=final` — модель завершила задачу, не зацикливаясь.

Если после `step=1 type=tool_call` идёт второй `tool_call` с тем же именем и аргументами — сработала защита от повторных вызовов (шаг 6.1): второй вызов пропускается, модели возвращается `ALREADY_EXECUTED`, и она переходит к финалу. В норме этого не происходит, но защита страхует.

### Известные ограничения текущей версии

- **Галлюцинации на неполных запросах.** На запрос `"Запиши заметку в файл"` без содержания модель может придумать заголовок («Не забыть купить хлеб»), которого в запросе не было. Если содержание важно — указывайте его явно в кавычках.
- **Маршрутизация read_notes vs search_notes на 3B нестабильна.** Модель иногда путает инструменты на неоднозначных формулировках. Если это происходит, уточните запрос: «по названию» или «по содержимому».
- **Стемминг — эвристика.** Поиск «покупки» → «покупок» работает, но «документы» → «документация» — нет. На шаге 7 (RAG с эмбеддингами) эта проблема закроется семантически.
- **Один инструмент за шаг.** Агент не умеет «сохрани заметку и сразу найди её». Для двух действий — два запроса.
- **Ответы на английском.** Иногда 3B-модель отвечает по-английски, даже если запрос на русском. Это ограничение модели, не архитектуры; переход на `qwen2.5:7b` уменьшает частоту, но замедляет работу на CPU.

## Проблемы и решения

**`ollama: command not found`**

Ollama не установлен или терминал не видит его. Переустановите Ollama и откройте новый терминал.

**`ConnectionError` при запуске агента**

Ollama не запущен. Выполните `ollama serve` в отдельном терминале или перезапустите Ollama.

**Модель отвечает очень медленно**

Это нормально для CPU. 3B-модель на CPU генерирует 5–15 токенов в секунду. Один запрос может занимать 30–120 секунд. Если совсем невыносимо — попробуйте `qwen2.5:1.5b` (быстрее, но качество ниже).

**`does not support tools` или модель не вызывает инструменты**

Убедитесь, что используете `qwen2.5-3b-agent` (созданную через Modelfile), а не `qwen2.5:3b`. Если не помогает — проверьте версию Ollama: `ollama --version`. Обновите, если она старше полугода.

**`ModuleNotFoundError` при запуске pytest**

Виртуальное окружение не активировано. Активируйте (см. шаг 4) и повторите.

**`FileNotFoundError: config/settings.toml`**

Вы не создали локальный файл настроек. Вернитесь к шагу 6.

**Тесты падают, но агент работает**

Возможно, окружение повреждено. Попробуйте пересоздать: удалите `.venv`, выполните `python -m venv .venv`, активируйте, установите зависимости заново.

**Хочу посмотреть, что делал агент**

Откройте `logs/agent.log`. Там видно, какие инструменты вызывались, какие были аргументы и что вернулось.
